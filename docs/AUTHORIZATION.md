# Authorization status

Bearer JWT identifies a user; the server reloads that user, compares the token tenant ID with the database, checks the school and subscription, and puts the school ID into the request's SQLAlchemy session. The session policy scopes tenant-owned ORM reads and writes and rejects cross-school foreign keys. Platform users use a separate scope and dedicated platform routes. A billing-only school administrator can access subscription routes after a trial expires, while ERP routes reject the token.

Role checks remain in each route. Student detail routes verify the student's own account; parents require a linked child; teachers require class or resource assignment in the reviewed paths. Assignment and study-material reads, submissions, grading and private file downloads include resource checks. Teacher reports and timetable are limited to assigned classes/subjects; student and parent timetable and assignment views are limited to their own class and section. Teacher profiles require staff access, and parent profiles require the matching parent identity. Two-school tests cover overlapping usernames, student and fee records, cross-school writes, and platform isolation. Regression tests cover the additional same-school profile/report/timetable checks and verify that role-specific portal aliases obey plan feature gates.

The full route-by-route role and resource ownership review requested for production is **not complete**. Session isolation is a defense in depth for cross-school data, not a substitute for same-school ownership checks. Some legacy routes may still expose same-school data to a role that should have narrower access. Finish a complete matrix and tests before customer onboarding.
